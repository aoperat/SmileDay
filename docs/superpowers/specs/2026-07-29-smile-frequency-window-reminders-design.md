# 미소 빈도·반복 중심 시간창 리마인더 설계

- 날짜: 2026-07-29
- 상태: 승인됨
- 제품 기준: 평소 잘 웃지 않는 사람이 일상에서 의식적으로 웃는 행동의 빈도와 반복을 늘리도록 돕는다.
- 대체 범위: `2026-07-28-situation-cards-and-contrast-design.md`의 상황 카드·시간대 분류 부분과 `2026-07-28-notification-smile-mvp-design.md`의 개별 알림 설정 부분

## 1. 제품 판단

현재 구현은 카메라·점수·얼굴 평가를 기본 흐름에서 제거하고, 짧은 미소와 완료 횟수를 기록한다는 점에서 제품 목적에 대체로 부합한다. 그러나 아침·낮·저녁으로 나뉜 14개 상황 카드, 사용자 카드 CRUD, 알림마다 시간과 카드를 따로 고르는 구조는 사용자가 반복 행동보다 분류와 설정을 관리하게 만든다.

새 핵심 루프는 다음 하나로 제한한다.

```text
활동 시작·종료 시간과 반복 주기 설정
→ 활동 시간 안에서 반복 알림
→ 짧고 비평가적인 생각 문구
→ 5초 미소
→ 완료 횟수 기록
→ 오늘과 최근 7일의 반복 확인
```

## 2. 현재 상태 판정

### 목적에 부합하는 상태

- 온보딩이 “원하는 시간에 알림을 받고 잠깐 미소 짓는 습관”을 제품 목적으로 설명한다.
- 기준선, 카메라, TrueDepth, 점수 없이 첫 실행부터 사용할 수 있다.
- 미소 완료는 사용자의 자기 보고이며 표정을 검증하거나 평가하지 않는다.
- 가이드가 5초로 짧고, 완료 시각이 `SmileMoment`로 온디바이스에 저장된다.
- 홈에서 오늘 완료 횟수와 최근 7일의 날짜별 횟수를 보여준다.
- 쉬어간 날을 실패로 표현하지 않는다.
- 수동 진입과 알림 딥링크가 모두 짧은 미소 실행 화면으로 연결된다.
- 사진·영상·서버 없이 동작한다.

### 목적에 일부만 부합하는 상태

- 여러 개별 알림은 빈도를 늘릴 수 있지만, 사용자가 매 시각을 직접 추가·수정해야 한다.
- “이번 주 활동 일수”는 꾸준함을 보여주지만 하루 안의 반복 빈도를 직접 설명하지는 않는다.
- 상황 카드는 행동 계기를 제공하지만 종류가 많고, 사용자의 핵심 설정 대상처럼 노출된다.
- 5초 신체 안내는 행동 시작에는 유용하지만, 매번 같은 종류의 지시만으로는 자연스러운 미소를 떠올리기 어렵다.

### 목적에 부합하지 않는 상태

- `DaySlot`의 아침·낮·저녁 레이블과 시간대별 추천은 제품에 필요 없는 의미를 부여한다.
- 14개 기본 상황 카드, 내 카드 추가·삭제·숨김·복구는 핵심 행동보다 콘텐츠 관리의 비중을 키운다.
- 알림마다 별도 상황 카드를 고르는 과정은 설정 마찰을 늘린다.
- 온보딩의 09:00·13:00·18:00 개별 알림 편집은 “활동 시간과 반복 주기”라는 더 단순한 모델과 맞지 않는다.
- 현재 14일 rolling 예약 방식은 앱을 오래 열지 않으면 알림이 끊기므로 장기 습관 도구에 적합하지 않다.
- 홈의 시간대별 추천 카드와 카드 선택 CTA는 “지금 한 번 웃기”보다 선택을 앞세운다.
- 레거시 얼굴 분석·기준선·케어 코드는 새 Root에서 도달할 수 없지만 여전히 빌드와 유지보수 부담을 만든다.

## 3. 리마인더 설정

사용자는 알림 시각 목록을 관리하지 않고 하나의 반복 설정을 관리한다.

기본값:

- 시작: 09:00
- 종료: 21:00
- 반복: 3시간마다
- 상태: 켜짐

설정 항목:

```text
미소 알림
[켜짐]

오전 9:00부터
오후 9:00까지
3시간마다
```

규칙:

- 시작 시각부터 종료 시각까지 계산한다.
- 시작 시각은 포함한다.
- 종료 시각은 반복 주기와 정확히 맞을 때만 포함한다.
- ~~자정을 넘는 시간창은 이번 범위에서 허용하지 않는다.~~ **2026-08-04 개정: 허용한다.** 아래 “자정을 넘는 시간창” 참고.
- ~~최소 반복 주기는 1시간으로 제한한다.~~ **2026-08-04 개정: 30분까지 허용한다.**
- 기본 선택지는 30분·1·2·3·4시간이며 직접 분 단위 입력은 제공하지 않는다.
- 생성되는 시각 예: 09:00~21:00, 3시간마다 → 09:00, 12:00, 15:00, 18:00, 21:00.
- 놓친 알림은 다시 울리거나 한꺼번에 보상하지 않는다.

### 자정을 넘는 시간창 (2026-08-04 개정)

원래 설계는 이 창을 범위에서 뺐고 §10에 후속 과제로 적어뒀다. 밤에 일하는 사용자는 22:00~02:00 같은 창이 활동 시간의 전부라, 그 창을 만들 수 없으면 이 앱의 핵심 루프 자체를 쓸 수 없다는 판단으로 허용한다.

- 종료가 시작보다 이른 시각이면 자정을 넘는 창으로 읽는다. 창의 길이는 하루를 더해서 잰다.
- 거부하는 조합은 **시작과 종료가 같은 시각**뿐이다 — 길이가 0인지 24시간인지 구분할 방법이 없다.
- `occurrences()`는 **창을 지나는 순서**로 돌려준다. 22:00~02:00/1시간이면 22, 23, 00, 01, 02다. 알림 문구가 이 순서로 돌기 때문에 사용자가 겪는 순서와 같아야 한다.
- 시계 순이 필요한 쪽(홈의 “다음 알림”)은 받아서 정렬한다. 창 순서를 그대로 믿으면 밤 11시에 이미 지난 00:00이 다음 알림으로 뜬다.
- 예약 자체는 달라지지 않는다. 각 시각은 여전히 매일 반복하는 `UNCalendarNotificationTrigger`다.
- 화면은 자정을 넘는 창일 때 “종료 시간은 다음 날로 봐요”를 함께 보여준다. 그러지 않으면 사용자가 잘못 고른 것으로 읽는다.

### 30분 주기 (2026-08-04 개정)

- 허용 주기는 30·60·120·180·240분이다.
- iOS는 앱 하나가 예약해둘 수 있는 알림을 64개까지만 들고 넘치면 **말없이** 뒤쪽을 버린다. 가장 촘촘한 30분 간격으로 하루를 다 써도 48개라 상한 안에 들어간다. `SmileReminderPatternTests`가 이 여유를 지키고, 더 짧은 주기를 넣는 순간 실패한다.
- 30분은 하루 최대 48회다. “재촉하지 않는다”는 원칙과 부딪힐 수 있으므로 §11의 7일 사용자 검증에서 부담을 확인한다.
- 미소를 완료해도 다음 예약 시각은 유지한다. 이번 범위에서는 자동 건너뛰기나 적응형 빈도를 넣지 않는다.

## 4. 저장 모델

새 SwiftData 모델 하나를 추가한다.

```swift
@Model
public final class SmileReminderSchedule {
    public var startHour: Int
    public var startMinute: Int
    public var endHour: Int
    public var endMinute: Int
    public var intervalMinutes: Int
    public var isEnabled: Bool
    public var notificationGroupID: String
}
```

- 앱이 사용하는 활성 스케줄은 최대 하나다.
- 저장소가 중복 레코드를 발견하면 가장 최근 레코드를 사용하되 자동 삭제하지 않는다.
- `ReminderSetting`은 기존 데이터 호환을 위해 스키마에 남기지만 새 화면과 스케줄링에서는 사용하지 않는다.
- `CustomSmileCard`, 숨긴 카드 설정, `guideID`도 기존 기록 해석을 위해 보존하되 새 사용자 흐름에서는 생성·수정하지 않는다.

시간 계산은 SwiftData 모델 밖의 순수 값 타입에서 수행한다.

```swift
public struct SmileReminderPattern: Equatable, Sendable {
    public let startMinutes: Int
    public let endMinutes: Int
    public let intervalMinutes: Int

    public func occurrences() throws -> [ReminderTime]
}
```

검증 오류는 시작≥종료, 허용되지 않은 반복 주기, 잘못된 시·분을 구분한다.

## 5. 알림 예약

각 계산 시각을 `UNCalendarNotificationTrigger`의 일일 반복 요청 하나로 예약한다.

- 예시 기본값은 총 5개의 repeating request를 만든다.
- 14일치 일회성 요청을 미리 쌓지 않으므로 앱을 14일 이상 열지 않아도 반복이 계속된다.
- identifier는 `notificationGroupID`와 시각으로 결정적으로 만든다.
- 설정 변경 시 기존 group identifier들을 먼저 취소하고 새 시각을 예약한다.
- 알림을 끄면 해당 group의 모든 요청을 취소한다.
- 권한 거부는 설정 저장을 막지 않으며 수동 미소는 계속 사용할 수 있다.
- 알림 제목은 “잠깐 웃어볼까요?”처럼 짧게 고정하고, 시간대나 상황 레이블을 넣지 않는다.
- 알림 본문은 “지금 괜찮다면 5초만 미소 지어보세요.”처럼 선택권을 준다.

반복 알림 자체에는 매번 다른 문구를 싣지 않는다. 반복 notification content는 고정하고, 알림을 탭한 뒤 가이드 화면에서 문구를 순환한다.

## 6. 미소를 돕는 문구

문구는 웃음을 명령하거나 외모를 평가하지 않고, 사용자가 편안한 표정을 떠올리게 한다. 분류명은 사용자에게 노출하지 않는다.

기본 카탈로그 예:

- “나를 아끼는 사람에게 어떤 표정을 보여주고 싶나요?”
- “반가운 사람을 만났을 때의 표정을 떠올려보세요.”
- “오늘의 나에게 따뜻한 표정을 보내볼까요?”
- “고마운 사람을 떠올리며 가볍게 미소 지어보세요.”
- “기분 좋은 인사를 건네듯 표정을 지어보세요.”
- “크게 웃지 않아도 괜찮아요. 편안한 미소면 충분해요.”
- “떠오르는 장면이 없어도 괜찮아요. 잠깐 얼굴의 힘만 빼보세요.”
- “지금 괜찮다면 입꼬리를 살짝 올려볼까요?”

문구 원칙:

- 타인의 평가, 사랑받을 자격, 외모 개선을 암시하지 않는다.
- 긍정적인 감정이나 좋은 기억을 강요하지 않는다.
- 최소 한 문장은 아무것도 떠오르지 않는 상태를 허용한다.
- 바로 전 문구와 같은 문구는 피한다.
- 문구 선택 상태는 로컬에 저장해 앱 재실행 후에도 순환을 이어간다.
- 사용자가 문구를 끌 수 있는 옵션은 첫 구현 이후 사용성 검증 결과에 따라 판단한다.

사용자가 제안한 “나를 사랑하는 사람이 나를 어떤 표정으로 봐줬으면 하나요?”는 의도는 맞지만 타인의 시선을 중심에 둔다. 기본 문구는 “나를 아끼는 사람에게 어떤 표정을 보여주고 싶나요?”처럼 사용자의 선택을 중심으로 표현한다.

## 7. 화면 변경

### 온보딩

- 대상과 목적을 명시한다: “평소 잘 웃지 않는 나를 위해, 하루에 몇 번 잠깐 웃어보는 시간을 만들어요.”
- 개별 알림 3개와 상황 카드 선택을 제거한다.
- 시작 시간, 종료 시간, 반복 주기만 확정한다.
- 계산된 하루 알림 횟수를 “하루 5번 알려드려요”처럼 미리 보여준다.

### 홈

- 최우선 정보: `오늘 미소 N번`.
- 최우선 행동: `지금 한 번 웃기`.
- 다음 알림 시각을 보여준다.
- “이번 주 활동 일수” 대신 “최근 7일 총 N번”을 보조 지표로 보여준다.
- 날짜별 횟수 도트는 유지한다.
- 상황 카드 선택 줄과 시간대별 추천을 제거한다.

### 미소 실행

- 실행할 때마다 순환 문구 하나를 보여준다.
- 중립적인 신체 안내 “턱과 어깨 힘을 빼고 편안하게 미소 지어보세요.”는 보조 문구로 고정한다.
- 5초 타이머, 중도 닫기 시 미기록, 완료 시 한 번 저장 규칙을 유지한다.
- 완료 문구는 “오늘 한 번 더 웃어봤어요.”로 빈도와 반복을 확인한다.

### 설정

- 개별 알림 CRUD, 카드별 선택, 미소 카드 관리 섹션을 제거한다.
- 시작 시간, 종료 시간, 반복 주기, 알림 켜기/끄기만 제공한다.
- 예상 알림 시각 목록은 읽기 전용으로 접어 보여줄 수 있다.
- 온디바이스 저장과 알림 권한 안내는 유지한다.

## 8. 피드백 지표

사용자 화면:

- 오늘 완료 횟수
- 최근 7일 총 완료 횟수
- 최근 7일 날짜별 완료 횟수
- 다음 알림

다음은 기본 화면에서 사용하지 않는다.

- 미소 점수와 얼굴 분석
- 아침·낮·저녁별 달성
- 상황 카드별 성과
- 연속 기록 손실
- 목표 미달 경고

제품 검증:

- 알림으로 하루에 실제 미소를 떠올린 횟수가 늘었는가?
- 시작·종료·반복 설정을 이해하기 쉬웠는가?
- 기본 3시간 주기가 부담스럽거나 부족하지 않았는가?
- 생각 문구가 자연스러운 미소에 도움이 되었는가, 부담이 되었는가?
- 알림 탭부터 완료까지 충분히 짧았는가?

## 9. 마이그레이션과 정리

- 새 스케줄이 없고 기존 `ReminderSetting`들이 정확한 등차 간격이면 시작·종료·간격을 제안값으로 변환할 수 있다.
- 기존 시각들이 불규칙하면 자동 변환하지 않고 기본값을 보여준 뒤 사용자가 저장하도록 한다.
- 새 설정을 사용자가 확정하기 전에는 기존 pending notification을 취소하지 않는다.
- 새 설정 저장과 예약이 성공한 뒤 기존 pending notification을 취소한다.
- 기존 SwiftData 모델과 기록은 이번 작업에서 삭제하지 않는다.
- 상황 카드 화면과 라이브러리는 Root에서 연결을 끊고, 배포·마이그레이션 상태 확인 후 별도 cleanup에서 삭제한다.

## 11. 완료 기준

- 앱 목적이 루트 지침과 온보딩에 동일한 문장으로 고정되어 있다.
- 사용자는 시작 시간, 종료 시간, 1·2·3·4시간 반복 주기로 알림을 설정한다.
- 아침·낮·저녁 레이블과 상황 카드 선택이 새 Root 흐름에 없다.
- 계산된 모든 시각에 일일 반복 알림이 예약되며 14일 후에도 자동으로 끊기지 않는다.
- 알림 탭 또는 수동 진입 시 비평가적 문구 하나와 5초 미소 화면이 열린다.
- 완료는 정확히 한 번 기록되고 오늘·최근 7일 횟수가 즉시 갱신된다.
- 기존 데이터가 삭제되지 않는다.
- 전체 `CoachingKit` 테스트와 앱 빌드가 통과한다.
- 실기기에서 허용·거부·설정 변경·앱 종료 상태의 반복 알림을 검증한다.
